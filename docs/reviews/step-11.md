# step11: Supabase の表と決まり

## 1. やったこと
- Supabase に東京のプロジェクト `temari` を作り、利用者・時間帯ごとの集計・体操の回数・10秒ごとの記録・スタッフ の5つの表を作った。
- 決まり（RLS）で「端末は匿名ログインで自分の行だけ書けて読める」「staff に登録したスタッフだけが全員分を読める」ようにし、判定用の関数は API から呼べない private スキーマに置いた。
- 10秒ごとの記録は 30 日たったら毎日自動で消すようにし、準備と運用の手順書を書いた。

## 3. 確認したこと・確認する手順
- 決まりのテストを Supabase の上で行った（テスト用の端末2台とスタッフ1人をその場で作り、最後に取り消した）。8項目すべて通った:
  1. 端末は自分の記録を足せて、同じ日・時間帯なら上書きできる
  2. 別の端末からは他人の利用者・記録が見えない
  3. 別の端末は他人の利用者IDで記録を書けない
  4. 端末は自分をスタッフに登録できない
  5. 端末は他人の利用者を乗っ取れない（auth_uid を書き換えられない）
  6. スタッフは全員の利用者を読める
  7. スタッフは全員の記録を読める
  8. ログインしていない人は何も読めない
- Supabase のセキュリティ・パフォーマンスの点検: 注意なし。
- 開発者が管理画面で行うこと: `docs/SUPABASE_SETUP.md` の 3 章（匿名ログインを有効にする・新規登録を止める）と 4 章（スタッフの登録）。

## 4. 判断を保留した点
- **匿名ログインの悪用**: 公開用の鍵を知っていれば、誰でも匿名ログインして「自分のデータ」を送れてしまう（他人のデータは読めない・書けない）。施設の外に配らないうちは問題になりにくいが、本番では送れる量の制限（レート制限）や CAPTCHA を考える。
- **10秒ごとの記録の量**: 1人 1日 最大 約 6,800 行。30 日で消すので 1人 約 20 万行。無料枠（500MB）に何人まで入るかは step12 のあとで実際の大きさを見て確かめる。
- **時刻**: `date` 列は端末の日付（日本時間）、`recorded_at` などは世界共通の時刻（UTC）で持つ。Web 画面では日本時間に直して出す。
- **端末を渡し替えたときのデータ**: 自動では消さない。手順書に消し方を書いた。
- **スタッフの登録**: 管理画面から手で行う。人数が増えたら Web 画面に登録の機能を作るか考える。
